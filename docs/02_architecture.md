# システム構成書

これはまだ**提案**です。理由を読んだ上で、認識が合っているか・変更したい点があるかを
教えてください。承認後に実装へ進みます。

## 1. 全体方針

本人1人だけが使うアプリだが、「毎日使い続ける長期プロダクト」であり、仕様変更が前提のため、
最初から保守性・拡張性を意識した構成にする。一方で初心者が最初から追える範囲に収める。

## 2. 全体構成図

```
┌─────────────┐        ┌──────────────────┐        ┌────────────────┐
│  フロントエンド │  HTTP  │     バックエンド     │        │  外部サービス     │
```

## 3. 技術選定と理由

### フロントエンド：React + TypeScript（Vite）

- 画面数が多い（ダッシュボード／ロードマップ／今日のタスク／振り返り／履歴・分析／設定）ため、
  素のHTML/JSより「部品化」できるReactの方が保守性が高い。
- TypeScriptにより、仕様変更でデータ構造が変わったときにエラーとして検知でき、
  初心者でも「どこを直せばいいか」が分かりやすい。
- 家計簿アプリ（同じDesktop内の別プロジェクト）は素のHTML/CSS/JSで作られているが、
  あちらは画面数が少なく単機能なため素のJSで十分だった。今回は画面・状態が多いため構成を変える。

### バックエンド：Node.js（Express）+ TypeScript

- Googleカレンダー連携には OAuth のトークン管理が必要 → ブラウザだけでは安全に扱えず、
  サーバーが必須。
- Claude APIの呼び出しにはAPIキーが必要 → フロントに置くと漏洩するため、サーバー経由にする。
- フロントと同じ言語（TypeScript）にすることで、初心者が学ぶ言語を1つに絞れる。

### データベース：PostgreSQL（Supabase を想定）

- 「理念→年→四半期→月→週→日」という階層構造や、振り返りの履歴などは
  テーブル同士の関連（リレーション）が中心になるため、リレーショナルDBが適している。
- Supabaseは無料枠があり、管理画面（GUI）からテーブルの中身を直接見られるため、
  初心者がデータの状態を目視確認しやすい。

### AI連携：Claude API（Anthropic）を、差し替え可能な抽象化の上に構築

- 振り返り内容を解析し、要約・改善提案・カレンダー変更案を生成する。プロダクトの中核機能のため、
  特定のAIベンダーにロックインされないよう、AI処理をアプリ本体から分離した構成にする。
- 詳細は本ドキュメント「7. AI連携アーキテクチャ」を参照。

### Googleカレンダー連携：Google Calendar API（OAuth 2.0）

- 今日のタスクをカレンダーへ反映／カレンダーの予定を読み取る双方向連携を想定。
- MVPでは「読み取り＋当日ルーティンイベントとの突き合わせ」を優先し、
  書き込み（自動更新）は運用後フェーズで段階的に有効化する（後述のロードマップ参照）。

### 認証

- 本人専用アプリだが、Googleカレンダー連携をするため、結局Google OAuthログインが必要になる。
  そのため追加のID/パスワード認証は作らず、**Googleアカウントでのログインのみ**にする
  （実装をシンプルにできる）。

### ホスティング

- フロントエンド：Vercel（もしくはRenderのStatic Site）
- バックエンド：Render（Web Service）
- DB：Supabase

過去の別プロジェクト（restaurant-url-finder）でもRender／GCPを使っており、
同じ運用パターンに揃えることで学習コストを抑える。

## 5. 検討した代替案と却下理由

| 代替案 | 却下理由 |
|---|---|
| 素のHTML/CSS/JS（家計簿アプリと同様） | 画面数・状態管理が増えると保守コストが急増するため今回は不採用 |
| Firebase（Firestore＋Functions） | NoSQLだと目標の階層構造や振り返り履歴の集計クエリが書きにくいため不採用 |
| ID/パスワード認証を別途実装 | Google OAuthと二重管理になり複雑化するため不採用 |

## 7. AI連携アーキテクチャ

AIはプロダクトの中核機能であるため、独立したレイヤーとして設計し、
「どのAIモデルを使うか」を後から変更できるようにする。

### 7.1 レイヤー分離の考え方

アプリ本体（振り返りAPI、目標API、カレンダーAPIなど）は、Claude APIやOpenAI APIの
細かい呼び出し方を知らなくてよい状態にする。間に共通のインターフェース（`AIProvider`）を挟み、
アプリ本体はそのインターフェースだけを呼ぶ。

```
振り返りAPI / 改善提案API
        │
        ▼
   AIProvider（インターフェース）
        │
   ┌────┴─────┐
   ▼          ▼
ClaudeProvider   OpenAIProvider（将来追加）
   │
   ▼
Claude API
```

### 7.2 ディレクトリ構成（backend内）

```
backend/src/ai/
├── AIProvider.ts        インターフェース定義（summarize, suggestImprovements, proposeCalendarChanges など）
├── ClaudeProvider.ts     Claude API を使った実装
├── prompts/              プロンプトのテンプレート（コードから分離）
│   ├── dailySummary.ts
│   ├── improvementSuggestions.ts
│   └── calendarChangeProposal.ts
└── index.ts              利用するProviderを選択するファクトリ（環境変数で切替）
```

- `AIProvider`はTypeScriptの`interface`として定義し、「振り返りを要約する」
  「改善案を提案する」「カレンダー変更案を作る」といったメソッドのシグネチャ（入出力の型）だけを決める。
- `ClaudeProvider`はそのインターフェースを実装し、内部でClaude APIを呼び出す。
- 将来OpenAIなど別モデルを使いたくなった場合、`OpenAIProvider`を追加し、
  環境変数（例：`AI_PROVIDER=openai`）で切り替えられるようにする。アプリ本体側のコードは
  変更不要にする。
- プロンプト文言は`ClaudeProvider`の中に直接書かず、`prompts/`以下のファイルに分離する。
  理由：プロンプトはAIモデルを変えたときや、提案の質を調整したいときに頻繁に見直す部分であり、
  ロジックと混在させると変更のたびにコード全体を読む必要が出てしまうため。

### 7.3 データの最小化

AIへ送信するデータは、その処理に必要な範囲に絞る。例えば「毎日の振り返り要約」であれば
当日の振り返り内容と関連する目標のタイトル程度に留め、無関係な過去の全履歴などは送らない。
将来のプロンプト設計時に、機能ごとに「何を送るか」を明記する。

### 7.4 提案〜承認〜反映のデータフロー

DB設計（[03_database_design.md](03_database_design.md)）の`ai_suggestions`テーブルに、
AIが生成した提案（要約・改善案・カレンダー変更案）とその理由、ユーザーの承認/却下結果を記録する。
AIは`ai_suggestions`にレコードを作るところまでを行い、実際のカレンダー反映や目標の更新は、
ユーザーが承認した場合のみバックエンドが実行する。AIが直接カレンダーや目標テーブルを
書き換えることはない。
