# 要件定義書

## 1. プロジェクトの目的

このアプリは「ToDoアプリ」でも「日記アプリ」でもない。
**人生の設計図を作り、その設計図に沿って毎日成長するためのシステム**である。

「何をするか」ではなく「どんな人になりたいか」を軸に人生を設計する。

## 2. 人生理念（現時点）

> 知識・健康・感性を磨き、AIを活用しながら社会へ価値を提供できる人になる。
> お金や自由は目的ではなく、価値提供の結果として得られるもの。

## 3. 優先テーマ

| 優先度 | テーマ | 位置づけ |
|---|---|---|
| 1 | AI | 柱（重点的に育てる） |
| 2 | 筋トレ | 柱 |
| 3 | 読書 | 柱 |
| 4 | 写真 | 毎日少しでも触れる |
| 5 | コーヒー | 毎日少しでも触れる |
| 6 | 歌 | 毎日少しでも触れる |

「柱」は投下時間が多くロードマップ上の目標を持つテーマ、「毎日少しでも触れる」テーマは
時間は短いが習慣として継続することが目的、という扱いの違いをデータ設計にも反映する
（詳細は [03_database_design.md](03_database_design.md) の `categories` テーブルを参照）。

## 4. 実現したいこと（全体像）

1. 人生理念の管理
2. 3〜5年後の人物像
3. 1年目標
4. 3か月目標
5. 月目標
6. 週目標
7. 今日やること
8. Googleカレンダーとの同期
9. 毎日の振り返り
10. AIによる改善提案
11. 過去データの蓄積
12. 自分専用の分析
13. ロードマップの自動更新

理念からタスクまでが一直線に繋がる「縦の階層構造」と、
振り返り→改善提案→翌日の計画への反映という「横のフィードバックループ」の
両方を成立させることが、このアプリの核となる要件。

## 5. 1日の流れ（アプリが支える体験）

```
朝  : Googleカレンダーを見る
    ↓
    今日やることを実行
    ↓
夜  : 振り返りを書く
    ↓
    AIが改善提案
    ↓
    必要ならGoogleカレンダーを更新
```

## 6. 現在の基本ルーティン（参考データ）

| 時間 | 内容 |
|---|---|
| 07:00 | 起床 |
| 08:00–08:30 | ニュース |
| 08:30–11:30 | AI学習 |
| 11:30–12:30 | 読書 |
| 14:00–16:00 | 筋トレ（火・木・土・日）／それ以外は自由時間 |
| 16:00–16:15 | 写真 |
| 16:15–16:30 | コーヒーソムリエ |
| 16:30–16:45 | 歌 |
| 18:00–18:30 | note執筆 |
| 23:00 | 就寝 |

Googleカレンダーには**毎日のルーティンのみ**を登録する。食事・自由時間・予定・デート・仕事などは
前日に空いている時間へ追加する運用とする。

## 7. 毎日の振り返り項目

- できたこと
- できなかったこと
- その理由
- 今日の学び
- 改善案
- 気分
- 集中度
- 睡眠

AIはこの内容を学習し、翌日以降の計画へ反映する。

## 8. AI連携（プロダクトの中核機能）

AIは補助的なチャット機能ではなく、**このアプリの中核機能**と位置づける。

### 8.1 AIが参照するデータ

人生理念／長期目標〜週間目標の階層／今日のタスク／毎日の振り返り／過去の達成状況／
気分・睡眠・集中度／できなかった理由／Googleカレンダー上の予定。

### 8.2 AIが行うこと

1. 毎日の振り返りを要約する
2. できたこと・できなかったことを分類する
3. 継続的に発生している課題を検出する
4. 翌日の改善案を提案する
5. 週間目標と日々の行動にズレがないか確認する
6. 長期目標から外れている場合は警告する
7. 過去の記録からユーザーの傾向を分析する
8. 実行しやすいタスクへ分解する
9. Googleカレンダーの変更案を作成する
10. ユーザーが承認した変更のみGoogleカレンダーへ反映する

### 8.3 基本フロー

```
ユーザーが振り返りを入力する
    ↓
振り返りをデータベースへ保存する
    ↓
AIが、目標・予定・過去の記録と照合する
    ↓
AIが以下を返す
  ・今日の要約
  ・課題
  ・原因の仮説
  ・明日の改善案
  ・予定変更案
  ・継続すべきこと
    ↓
ユーザーが内容を確認する
    ↓
ユーザーが承認した変更だけを反映する
```

### 8.4 重要な制約

- AIが勝手に予定を変更しない
- AIが勝手に目標を書き換えない
- AIが勝手に人生理念を変更しない
- 変更は必ず「提案 → ユーザー承認 → 反映」の順番にする
- AIの提案理由を表示する
- AIの提案履歴を保存する
- ユーザーが提案を却下した場合、その結果も記録する
- AIが判断できない場合は、推測で変更せず質問する

### 8.5 設計上の要件

- AIモデルは後から変更可能にする（最初はClaude APIを使うが、将来OpenAI APIなど他モデルへ
  切り替えられるよう、AI処理をアプリ本体から分離する。詳細は
  [02_architecture.md](02_architecture.md) のAI連携アーキテクチャを参照）
- プロンプトはコードに直接書き散らさず、管理しやすい形で分離する
- AIへ送信するデータは必要最小限にし、個人情報や振り返りデータの扱いを明確にする

## 9. MVPスコープ（最初に完成させる範囲）

1. 人生理念
2. ロードマップ（3〜5年後の人物像 〜 週目標の階層）
3. 今日のタスク
4. Googleカレンダー同期
5. 毎日の振り返り
6. AIによる改善提案（MVPでは以下の5つに限定）
   1. 毎日の振り返り要約
   2. 明日の改善案を最大3件提示
   3. Googleカレンダーへの予定変更案作成
   4. ユーザー承認後のカレンダー反映
   5. AI提案履歴の保存

高度な長期分析（傾向分析・週間目標とのズレ検知など）や、ロードマップの自動再構築は
MVP運用後に追加する。

MVP完成後は一度運用を開始し、実際に使いながら改善・機能追加を重ねる。

## 10. スコープ外（MVPでは作らないもの）

- 過去データの高度な分析ダッシュボード（グラフ等は運用後フェーズ）
- ロードマップの完全自動更新（最初はAI提案を人が見て手動反映）
- 複数ユーザー対応（本人専用の1ユーザーアプリとして設計）
- モバイルアプリ化（まずはWebアプリ）

## 11. 非機能要件

- **保守性・拡張性**：仕様変更が前提。テーブル・画面・APIは疎結合に設計する。
- **プライバシー**：本人専用データのため外部公開しない。GitHubはPrivate Repositoryで管理する。
- **初心者向け説明責任**：実装だけでなく設計意図を都度説明する。
- **段階的な開発**：一度に作り込みすぎず、小さく作って動作確認を繰り返す。

## 12. ステークホルダーと役割分担（AI側の振る舞い）

Claudeは以下を兼務する。

- 人生コーチ／習慣コーチ：振り返りや目標設定に対してフィードバックする
- プロダクトマネージャー：要件を整理し、機能の優先順位を提案する
- エンジニア：設計・実装を行う
- データアナリスト：蓄積データから傾向を読み取り、改善提案の根拠にする

仕様を勝手に変更せず、変更提案がある場合は理由を添えて提案する。
